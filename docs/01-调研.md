# 阶段一 · 调研报告

> 项目：《明日方舟：终末地》自动配队 + 输出轴推荐系统
> 调研日期：2026-10-25
> 结论先行：**可行，但必须换掉“全自动精确模拟”这个目标**。可交付的是一条
> “数据自更新 → 语义结构化 → 帧级仿真 → 轴搜索 → 配队排序”的流水线，
> 其中**数值精度分级**（哪些结论算硬结论、哪些只是排序参考）必须对用户可见。

---

## 1. 为什么这个项目抽象、又为什么它能做

用户的悲观是有道理的，但悲观点需要重新定位。真正难的不是“推荐配队”，而是：

| 难点 | 本质 | 本项目怎么处理 |
|---|---|---|
| 名词/角色/机制频繁变动 | 数据是**流**不是**静态表** | 数据层版本化 + 漂移检测（P0） |
| 技能文本是自然语言 | 语义 → 可执行的触发条件 | 规则抽取为主，LLM 兜底（P1） |
| 受击依赖 | 敌人行为不确定 | 显式建模“敌人攻击时间表”为**场景输入**，不假装知道 |
| 主控重击速度不同 | 需要**帧数据** | 已找到 `durationFrame / exclusiveFrame`（30fps），直接量化 |
| 输出轴是组合优化 | 搜索空间爆炸 | 帧级离散事件 + beam search（P2/P3） |

**结论：难点不在“算伤害”，在“把游戏规则变成数据”。** 而这次调研确认：
游戏规则**已经以数据形式存在**（客户端拆包表 + 社区 Wiki），只是没人把它整理成
“配队搜索”能直接用的形状。这就是本项目的价值空间。

## 2. 游戏机制调研

### 2.1 队伍与技能结构

- 编队 **4 人**，每人各提供 **战技（battle skill）**、**连携技（combo skill）**、
  **终结技（ultimate）**，外加普攻/下落攻击/处决攻击。
- **战技无冷却**，消耗 **1 段技力**；**全队共享 3 段技力**，自然恢复，
  也可通过 **普攻最后一段（重击）**、**闪避敌人攻击**、**处决失衡敌人** 等方式回复。
- **连携技**有独立冷却（3–40s）和**各自的触发条件**（如“重击命中”“干员受击后”
  “敌人处于 XX 状态”），触发后有约 **5 秒窗口**可以插入。
- **终结技**需要攒满**终结技能量**（70–300 不等），长按战技释放；
  使用战技与连携技可累积终结技能量，冷却 10–20s。

来源：[360《终末地》战斗系统教学（物伤与元素机制详解）](http://360game.360.cn/article/content?id=697198fb79aece0ce4401f31)；
数值来自客户端表 `SkillPatchTable` / `MediaWiki:Skilldata.json`（见 §3）。

### 2.2 重击与主控差异（用户点名的痛点）

数据层直接给出了每个技能动画的帧长度（**30 FPS**，已由社区对 626 个动画条目验证）：

```
陈千语 普攻 1–5 段：exclusive = [19, 15, 22, 30, 42] 帧，合计 128 帧 = 4.27s（可取消链）
                     duration  合计 606 帧 = 20.20s（完全不取消时的全长）
                     power_attack（重击）：exclusive 50 帧，duration 154 帧
```

**模型含义**：`exclusiveFrame` = 不可打断的承诺帧，之后玩家可取消进入下一个动作；
`durationFrame` = 自然播放到底的长度。因此“主控普攻连段速度不一致”**可以被精确量化**，
不需要靠手感估；轴搜索的自由度正是“是否提前取消”。

> 关键洞察：轴优化不是“排技能顺序”，而是**在帧级承诺约束下排动作**。
> 这就是为什么必须做时间轴而不是做技能循环表。

### 2.3 失衡与处决

- 重击与技能命中累积**失衡值**（poise），敌人有 `MaxPoise`（默认 0）与
  `PoiseRecTime`（默认 10s）。
- 敌人失衡时可处决（大量物理伤害 + 回复技力）。
- 带红圈的蓄力攻击可用技能打断并追加失衡。

### 2.4 元素与异常（两套独立系统）

- 五个元素：**物理 / 灼热 / 电磁 / 寒冷 / 自然**（另有「超域」，见 `数值范围` 页）。
- **法术异常**三阶段：附着 → 爆发 → 异常。
  灼热→燃烧、电磁→导电、寒冷→冻结、自然→腐蚀；异常种类由“第二个元素”决定。
- **物理异常**四类：击飞 / 倒地 / 猛击 / 碎甲。
  击飞、倒地负责叠「破防」（最多 4 层）；猛击、碎甲**消耗**破防层数打爆发。
  因此连招原则是：叠破防 → 消耗。
- 源石技艺强度（AI）会缩放异常/爆发伤害与效果强度，有三条不同曲线。

来源同上，以及 `数值范围` 页的属性表（[wiki](https://wiki.biligame.com/zmd/数值范围)）。

### 2.5 伤害公式（社区已收敛）

```
DMG = ATK × BaseMult × DMGBonus × Crit × Amp × Stagger × Finisher × Link
      × Weakness × Susceptibility × IncreasedDMGTaken × DMGReduction
      × Protection × DEF × RES × Multiplicative
```

- `ATK = ((干员ATK + 武器ATK) × (1+ATK%) + 固定) × (1 + 0.005×主属性 + 0.002×副属性)`（主/副属性取整后参与）
- `DEF` 项 = `100/(DEF+100)`；敌人普遍 100 DEF（×0.5）
- 失衡中 ×1.3（独立乘区）
- 同一侧 `NormalCalcZone` 内部相加，`ProdCalcZone` 分别相乘
- 反应：爆发 160%、异常 80%+80%/层、击飞/倒地 120%、猛击 150%+150%/层、碎甲 50%+50%/层、
  燃烧 12%+12%/级、冻结 120%+120%/级
- 等级系数：法术/冻结 `1+(Lv−1)/196`，物理状态 `1+(Lv−1)/392`
- 最终伤害四舍五入到整数

来源：社区共识（Talos Wiki / GameKee / 666bj《终末地数据机制导论》），
并经 `BattleConst` 表与 `BuffData` 校准；详见参考文档 `docs/reference/docs__data-sources.md`。

**警告**：本项目只实现能接地（grounded）的乘区，其余默认 ×1 并在结果里显式标注
`unmodeled_zones`，绝不假装算全。

## 3. 数据源评估（关键结论）

### 3.1 客户端拆包表（最权威、可机读、有版本）

| 源 | 内容 | 状态 |
|---|---|---|
| [rmxlinux/EndfieldData](https://github.com/rmxlinux/EndfieldData) | `TableCfg/`（角色/技能补丁/常量/属性）+ `Json/SkillData/`（每技能一文件，含帧数据）+ `Json/BuffData/` | **首选**。2026-10-23 更新（1.6），65k 文件 |
| [4n3u/EndfieldResourceData](https://github.com/4n3u/EndfieldResourceData) | 同类备份，2026-10-23 | 交叉校验用 |
| [luosky/EndfieldDataRmxLinux](https://github.com/luosky/EndfieldDataRmxLinux) | TableCfg 备份，2026-03（1.1，已旧） | 只作历史快照 |

关键表：
- `CharacterTable.json`（8.1 MB）：干员基础属性、成长、突破、职业、标签
- `SkillPatchTable.json`（7.6 MB）：**所有技能的各等级倍率/能量/冷却**（每技能 12 级）
- `BattleConst.json` / `AttributeMetaTable.json`：伤害公式常量、属性枚举
- `Json/SkillData/<skillId>.json`：`durationFrame`、`exclusiveFrame`、`offsetRecordFrame`、
  `timelineActions`（每个 `DamageAction` 的起始帧）、`castData.costData`
- `Json/BuffData/<buffId>.json`：buff 时长/叠层/属性修正/伤害乘区

> 这是本项目能做到“帧级轴”的**唯一**原因。

### 3.2 Wiki（人类语义、中文名、更新快）

| 源 | 接口 | 用途 |
|---|---|---|
| [BWIKI 终末地](https://wiki.biligame.com/zmd/) | MediaWiki 1.37 + **Semantic MediaWiki** | 干员列表/职业/属性/TAG（`action=ask` SMW 查询） |
| `MediaWiki:Skilldata.json` | 单文件 JSON（144 KB） | 全干员技能倍率（与表对齐，适合做**漂移检测**） |
| 干员页 wikitext | `action=parse&prop=wikitext` | 技能**中文描述**、天赋、潜能（语义抽取的输入） |
| `<干员>/详细数据` | wikitext 表格 | 1–90 级属性成长 |
| `MediaWiki:EnmAttrData.json` | JSON | 敌人属性 |

已验证可用（本机实测 200 OK）：
```
https://wiki.biligame.com/zmd/api.php?action=ask&format=json&query=[[分类:干员]]|?干员代号|?稀有度|...
https://wiki.biligame.com/zmd/api.php?action=query&list=allcategories&aclimit=500
```
注意：BWIKI 自身标注“数据仍在完善”，部分新干员缺 `/详细数据`；`干员` 分类 30 项，
`Skilldata.json` 只覆盖 23 人 —— **覆盖率不足是真实约束**，必须做覆盖率报告。

## 4. 前作评估（不要重复造轮子，但也不要照抄）

调研中发现 4 个高度相关项目，必须明确“借鉴什么、不借鉴什么”：

| 项目 | 状态 | 可借鉴 | 不借鉴 |
|---|---|---|---|
| [jojkaart/Endfield-battle-simulator](https://github.com/jojkaart/Endfield-battle-simulator) | 活跃（2026-10-25），TS，479 文件 | **数据源评估方法论**、帧率结论、伤害公式共识、`SkillData` 格式笔记、100 条 in-game 待验清单 | 它靠**手写 40+ 干员 kit** 才能跑；我们无法在单轮内复刻 |
| [mitchell-ma/zero-sanity-timeline](https://github.com/mitchell-ma/zero-sanity-timeline) | 2026-05 | 战斗模拟器 + 伤害计算器的分层思路 | 覆盖范围小 |
| [nn971/EndfieldAxis](https://github.com/nn971/EndfieldAxis) | 2026-03 | 单页仿真器交互 | 无 licence，不可抄代码 |
| [yjlovegy/endfield-assistant](https://github.com/yjlovegy/endfield-assistant) | 2026-10-25 | 配队 + 技能轴编辑的产品形态 | 闭源发布，不可复用 |

**判断**：前作走的是“手写每个干员的 kit → 高精度”路线，代价是**人力**（100 条待验测试、
4 个 batch、一周以上）。本项目走**“数据驱动 + 语义抽取 + 概率分级”**路线：
精度更低，但**能自更新**，且能在数据更新后自动重跑。这是差异化，也是用户明确要的
（“Wiki 同步信息自更新”）。

## 5. 风险登记册

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 干员数据覆盖率不足（23/30） | 配队池缺失 | 覆盖率报告 + 缺数据干员降级为“仅标签”参与排序 |
| R2 | 技能语义抽取错误 | 触发条件错 → 轴不可执行 | 规则+LLM 双通道 + 分歧报告 + 缓存人工复核 |
| R3 | 伤害公式未接地乘区 | 绝对 DPS 不可信 | 只输出**相对排序**与置信度；`unmodeled_zones` 显式暴露 |
| R4 | 敌人行为不可知（受击依赖） | 轴依赖外部输入 | 敌人攻击时间表作为**场景参数**，提供默认模板 |
| R5 | 版本更新破坏表结构 | 同步失败 | schema 版本 + 漂移检测 + 失败不覆盖旧数据 |
| R6 | LLM 幻觉数字 | 输出错误数值 | **LLM 禁止产出数值**，只产出语义标签与解释 |
| R7 | 搜索空间爆炸 | 跑不出结果 | 帧级 beam search + 剪枝 + 时间上限 |

## 6. 调研结论

1. **“帧级轴”是可达的**，因为拆包表里有动画帧与命中帧 —— 用户担心的“重击速度不同”已被数据解决。
2. **“自更新”是可达的**，因为权威数据在 GitHub、语义数据在 Wiki API，两者都有版本锚点。
3. **“精确 DPS”不可达**（单轮），因此产品定位必须是**排序器 + 可解释建议**，不是“伤害真值机”。
4. **LLM 的正确位置是语义与解释，不是数值**。这条必须写进架构，否则一定会翻车。
5. 前作已经证明这条路要 100+ 条实测校准；本项目选择**降低精度、换取自更新与覆盖率**，
   并在输出里**分级标注置信度**——这是对用户悲观预期的正面回答。
