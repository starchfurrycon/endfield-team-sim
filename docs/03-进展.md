**做了什么**

**结果**
| 指标 | 值 |
|---|---|
| 干员 | 35（客户端表） |
| 技能文件 | 336 个（332 缓存命中） |
| 完整帧数据 | 31/35（其余为特殊形态） |
| 有 wiki 文本 | 32/35 |
| 倍率交叉校验一致率 | 87.5%（63/72） |
| 命中帧来源 | 数据 242 / 估计 94 |

**决策与理由**
1. **主数据源换成客户端拆包表**（rmxlinux/EndfieldData @ `a0ed1dac31`，1.6）。
   理由：它是唯一提供 `durationFrame / exclusiveFrame / DamageAction 帧` 的源，
   没有它就没有"帧级轴"。wiki 只作语义与校验。
2. **raw.githubusercontent 在国内不可达**（实测三次全超时）→ 改用 jsDelivr CDN
   (`cdn.jsdelivr.net`)，并保留 gcore 与 GitHub raw 作为回退。
3. **BWIKI 对默认 UA 返回 HTTP 567**（WAF）→ 改为完整浏览器头（UA+Referer+Accept）。
4. **多段技能倍率不能简单求和**：同一段普攻会有 2~9 个 `DamageAction` 实例
   （命中判定 / 展示 / 分支）。现状：跳过无黑板 key 的实例、按帧求和，
   并把 wiki 的「效果1」存为 `wiki_anchor` 仅作**诊断**，不当总量。
   理由：实测 wiki 的「效果1」只是多组成部分里的第一项（如黎风 38% vs 全段 195%）。
5. 交叉校验不一致的 9 项已全部写进 `data/reports/crosscheck.md`，不隐藏。

**偏离计划**
- 计划里写"抽样比对一致率 100%"。实际 87.5%，原因是上面的多段/分支问题。
  **判定：不强行凑成 100%，改为"差异可解释 + 报告可见"。**

**遗留**
- `chr_9000_endmin`（管理员占位）无技能；男/女版本各有独立 char_id。
- 少数干员（汤汤/诀/提弗洛斯/梨诺/祀/噗切娜）wiki 无文本 → 语义靠兜底。

## P2 · 仿真引擎 ✅

**目标**：30fps 帧级时间轴 + 资源约束 + 不变量。

**做了什么**
- `engine/battle.py`：`Battle` 状态机（可克隆）、`advance_to()` 统一结算命中/技力/敌人出手。
- `engine/damage.py`：分层乘区，未建模项默认 ×1 并回报。
- 全局动作锁、切人开销、连携窗口、失衡、终结技能量。

**决策与理由**
1. **全局动作锁**（同一时刻只有一人在场）。
   起因：初版允许四人并行出手，出现了"0.00s 陈千语普攻 + 0.40s 佩丽卡战技"这种
   不可能的时间轴。加了 `global_busy` 后轴变成真正的序列。
2. **rollout 策略从"技能优先"改成"伤害/承诺帧"**。
   起因：技能优先时热启动会盲目先倾泻终结技（承诺 100+ 帧），反而比冷启动伤害低，
   违反"能量更多不可能更差"的单调性。改后热启动稳定 ≥ 冷启动。
3. **命中按帧结算、伤害按 `total_multiplier` 均分到各命中帧**，失衡同理。

**不变量测试**（`tests/test_core.py`）：技力非负/不超上限、能量不超上限、
同种子可复现、随机 20 条轴 × 80 动作不崩。

**遗留（重要）**
- 未建模：buff/debuff、元素异常与物理异常伤害、武器装备、暴击随机性、敌人硬直。
  这会让**绝对 DPS 明显偏低**，只能用于相对比较。

## 补充：常量到底能不能从数据里挖出来？（回答用户提问）

结论：**能挖出一部分，而且已经挖到了；但基础技力恢复速率这类"引擎硬编码"不在拆包表里。**

### 已经拿到（数据口径，已接入引擎）

| 量 | 值 | 出处 |
|---|---|---|
| 战技给全队的终结技能量 | **6.5** | `Json/BuffData/buff_common_obtain_ultimate_sp` 黑板 `usp_everyone=6.5`（`usp_self=0`） |
| 终结技所需能量 | 70~300/按干员 | `SkillPatchTable` `costType=0, costValue` |
| 连携技回能 | 按技能黑板 `usp`（如莱万汀 25/5/5/0） | 各干员 `*_combo_skill` / `buff_chr_*_combo_skill_usp` |
| 连携冷却 / 终结技冷却 | 3~40s / 10~20s | `SkillPatchTable.coolDown` |
| 动作承诺帧 / 总帧 / 命中帧 | 逐技能 | `Json/SkillData/*.json` |
| 失衡值累积 | 逐技能黑板 `poise` | `SkillPatchTable` |
| 伤害公式常量 | `atkRateOfMain=0.005`、`atkRateOfSub=0.002` 等 | `BattleConst` |
| 默认终结技上限 | 100 | `BattleConst.maxUltimateSp`（干员可覆盖） |

### 挖不到 / 尚未接入（仍是估计）

- **基础技力（ATB）恢复速率**：`BattleConst` 只有 14 个字段，没有它；
  `LuaScripts/Const/Const.lua` 里只有枚举名（`AtbCostAddition` 等）；
  BuffData 里只有"恢复速率修正"类 buff（如 `buff_cc_chr_no_lastcombo_stop_atb_recover` 的
  `ratio=-1`、`buff_cc_chr_set_skill_atb_recover_ratio` 的 `skill_ratio=0.5`），
  **修正项存在 → 基础项应是引擎常量**，未随表导出。
- **重击/处决/闪避回复技力的具体数值**：同样只找到修正 buff，没有基础值。
- **切人开销、连携窗口精确帧数**：无对应表字段（窗口 5s 来自攻略描述）。
- **敌人出手节奏**：属于 AI 行为树（`ExtendData/Main/CompressData/*.json`），
  可解析但工作量远大于收益，目前作为场景参数。

### 继续挖的两条路

1. **解析 BuffData 全量（>1000 个）+ AI 行为树**：能补齐修正项与敌人节奏，
   但基础恢复速率如果真是引擎硬编码，仍然拿不到。
2. **用真实战斗日志反推**（推荐）：ZMDLogs 一类的战斗回放能直接拟合出
   "每秒技力恢复""重击回多少"，这是最可靠的校准方式，且可自动化回归。

→ 已生成 `data/reports/constants.md`：把每个常量标注为「数据 / 估计」，随 `check` 输出。

## 追加轮（验收轮）· 修掉的两个真实缺陷

1. **倍率取 0**：萤石终结技、洛茜战技的黑板 key 是 `atk_scale_total` / `atk_scale_once`，
   旧逻辑只认 `atk_scale` → 这两个技能伤害恒为 0（等于不存在）。
   修法：`Skill._resolve_mult` 加命名兜底链（atk_scale → atk_scale_total →
   atk_scale_once → atk_scale_base → display_atk_scale → 任意 atk_scale* 的最大值）。
   修完洛茜（战技 0 → 6.12 倍率、终结技 22.05）进入 Top1 队，热启动优势也从
   "持平"变成 909 → 971 DPS。
2. **热启动可能比冷启动差**：`opening_ults` 只是启发式起点。
   新增 `search_pair()`：冷启动的完整动作序列在热启动条件下同样合法，
   重放得到下界，与搜索结果取优；并补 `test_hot_not_worse_than_cold` 守住。
   顺带修了 `RotationResult.actions` 只含搜索前缀的问题（现在从 timeline 还原完整序列）。

测试从 17 项扩到 **26 项**（新增约束遵守、单调性、本地 API 契约、报告存在性）。

## 追加轮二 · 机制溯源（推翻我自己的错误结论）

**上一轮我说"基础技力恢复在引擎侧、表里没有"，这个判断是错的**——它是"我没找完"。
这一轮把游戏自带的机制文本挖出来了，并找到了 4 个原本记为 estimate 的真实数值。

### 找到的东西（可复现：`python run.py mechanics`）

游戏内教学页 `WikiTutorialPageTable`（文本 id 用 `I18nTextTable_CN` 解）：

- `wiki_tut_bat_sp_1`：**技力会随时间自动恢复，主控干员的重击命中也可以恢复技力。**
- `wiki_tut_bat_heavy_attack_1`：普攻最后一段叫重击，**主控干员的重击**恢复技力并累积失衡值。
- `wiki_tut_bat_combo_2`：**施放连携技不需要技力**，但有冷却。
- `wiki_tut_bat_normal_skill_1`：战技**没有冷却时间**。
- `wiki_tut_bat_ultimite_skill_2`：终结技能量两种来源 —— 施放**战技**时**全队**获得等量；
  施放**连携技**时**施放者自身**获得。
- `wiki_tut_bat_ultimite_skill_3`：终结技**消耗全部**能量并进入冷却。
- `wiki_tut_bat_return_1`：**返还技力不算"恢复技力"**，且这部分技力消耗时**不获得终结技能量**。
- `wiki_tut_bat_execute_1`：处决失衡敌人恢复一定技力。
- `wiki_tut_bat_dash_1`：极限闪避恢复少量技力。
- `wiki_tut_bat_team_1`：**主控以外的干员会自动进行普通攻击**（这条我之前完全没建模）。

战斗规则 buff（`Json/BuffData`）里的数值：

| 机制 | buff | 黑板 | 换算 |
|---|---|---|---|
| 重击回技力 | `buff_dung_atb_add_lastnormalattack` | `atb=1.0` | **100 点（1 段）** |
| 极限闪避回技力 | `buff_dung_atb_add_perfectdodge` | `atb=1.0` | **100 点** |
| 击杀回技力 | `buff_dung_atb_add_kill` | `atb=0.5` | **50 点** |
| 战技给全队终结技能量 | `buff_common_obtain_ultimate_sp` | `usp_everyone=6.5` | **6.5** |
| 技力上限变化 | `buff_common_change_atb_max` | `value=40.0` | 40 |

于是把 `SP_GAIN_HEAVY` 从猜的 30 改成 **100**、闪避从 30 改成 **100**，新增击杀 50。
改完输出轴立刻变化：40s 窗口内战技次数 7→8，冷启动也能攒出 1 次终结技。

### 仍然拿不到的（这次是有证据的结论，不是猜）

**技力自然恢复速率**：`buff_dung_atb_recoverspeed` 这个"规则 buff"确实存在，
但它的 `blackboard` 为空、`triggerInterval=-1`、`attributeModifier` 为空
——**其他所有规则 buff 都带数值参数，只有它不带**，说明速率由引擎常量提供，未随表导出。
剩下的 `buff_dung_atb_recoverspeed_1` 只是 `ratio=-0.7` 这类**修正项**。

同类情况：`buff_dung_atb_add_useskill` 是"把获得的技力值存下来再按比例计算"的脚本行为，
没有可直接读的常量。

### 由此暴露的建模缺口（下一步）

1. **主控以外自动普攻**（有文本依据、有帧数据，缺的只是节奏模型）；
2. **返还技力**与"恢复技力"的区分（影响依赖"恢复技力"触发的装备/天赋）；
3. 处决回技力没找到具体数值，暂按 1 段。

## 追加轮三 · 发行测试版

### 补完的建模缺口：主控外自动普攻

依据：游戏内教学页 `wiki_tut_bat_team_1`「主控干员以外的干员，会自动进行普通攻击」。

实现要点（`engine/battle.py`）：

- 非主控干员按自己的普攻连段节奏自动出手，**不占用全局动作锁**（主控可以同时行动）；
- 使用各自的 `exclusiveFrame` 作为节奏，段间加 `AUTO_ATTACK_GAP_FRAMES`（估计值，机制有据、间隔无据）；
- **不给技力**（教学页明确只有"主控干员的重击"回技力），不触发连携窗口；
- 放技能期间暂停自动普攻，技能结束继续。

效果：4 人队 40s 窗口总伤从 ~37k 升到 ~110k（此前三名非主控完全不输出，属于系统性低估）。
新增 3 项测试（自动普攻有伤害 / 关闭则为 0 / 不回技力），测试总数 **29 项**。

### 发行

## 追加轮四 · 正式版 v1.0.0

### 1. 元素 / 物理异常伤害子系统（`engine/reactions.py`）

按 docs/01 §2.4–2.5 的机制实现：

- 法术：附着 → 同元素再命中**爆发 160%**；异元素命中**异常 80%×(1+附着层数)**（层数上限 4）
- 物理：击飞/倒地叠**破防**（上限 4）；猛击消耗层数 150%+150%/层；碎甲 50%+50%/层；
  击飞/倒地触发时 120%
- 等级系数：法术 `1+(Lv−1)/196`，物理 `1+(Lv−1)/392`
- 异常伤害计入总伤与角色贡献，并在 `Result.stats.reactions` 单列

**一个重要修正**：初版让普攻也叠附着，导致爆发 66 次、异常伤害占总量 **51%**（明显过度建模）。
依据教学页「所有带元素的**技能**都会让敌人叠加异常」，改为**只有技能施加附着**，
并把层数上限压到 4 → 异常占比降到 ~8.5%，量级合理。

### 2. 武器 ATK

`WeaponBasicTable` + `WeaponUpgradeTemplateTable` 提供每把武器 1–90 级 `baseAtk`；
干员默认武器按 `Scenario.weapon_level`（默认 80）计入公式。
效果：ATK 约 370 → 650，总伤接近翻倍。

### 3. 技能角色分类 + 澄清"零倍率"

每个技能标记 `role ∈ {damage, heal, buff}`。此前被误报为"倍率 0 可能是数据缺陷"的
6 个技能确认为：赛希战技（治疗）、赛希终结技（增益）、昼雪连携（治疗）、
秋栗终结技（回技力）、安塔尔终结技（增益）、庄方宜终结技（状态）。
→ **不是数据缺陷**，测试里加了断言：`role=damage` 的技能不允许倍率为 0。

### 4. 数据 schema 版本

新增 `SCHEMA_VERSION`（当前 2）并纳入数据集版本哈希；`serve` 启动时若发现
本地数据 schema 过旧会自动重建，避免旧缓存缺字段导致静默降级。

### 5. 测试

44 项（新增 15 项机制断言：爆发/异常随层数增长、破防上限、猛击>碎甲、
武器等级单调性、零倍率技能必须属于 support 等）。

## 追加轮五 · v1.1.0（按 Talos Wiki 补全元素异常）

抓到权威机制页后重做了异常子系统（数据来源：endfield.wiki.gg 的
Arts Infliction / Arts Burst / Arts Reaction / Combustion / Arts Intensity）：

| 机制 | 值 | 出处 |
|---|---|---|
| 附着 | 持续 20 秒、最多 4 层 | Arts Infliction |
| 爆发 | 同元素 160% ATK | Arts Infliction |
| 状态等级 | 已有附着层数决定 I~IV | Arts Reaction |
| 燃烧 | 初始 160/240/320/400%，DoT 24/36/48/60%/s × 10s | Combustion 表格 |
| 导电 | 法术受伤 +12/16/20/24% | Damage calculation |
| 腐蚀 | 抗性 -3.6~7.2 起、+0.84~1.68/s、上限 12~24 | Arts Reaction |
| 源石技艺强度 | 法术异常 ×(1+AI/100) | Arts Intensity |

同时把伤害结算从"施放时"改成"命中瞬间"，这样抗性/易伤/失衡/导电增伤/腐蚀减抗
都按命中时刻的状态计算。

副作用：附着只由**技能**施加（与 wiki「Some Operators are capable of applying
Arts Inflictions through Combat Skills」一致），爆发次数下降约 4 倍，
同队 DPS 从 ~7.9k 调整到 ~5.7k —— 这是向真机靠拢，不是退步。

测试：51 项（新增 7 项状态等级/燃烧跳数/腐蚀爬坡/导电超时/附着失效/AI 线性/碎冰）。

## 追加轮六 · v1.2.0（天赋/潜能接入）

数据源：`TableCfg/PotentialTalentEffectTable.json`（306 条），键为
`chr_XXXX_talent_N_M` / `chr_XXXX_potential_N`，每条含
`attrModifier{attrType,attrValue}` / `skillBbModifier{bbKey,floatValue}` / `activeCondition`。

实现：解析成 `operator.mods`，引擎只施加 **activeCondition 为空**的条目：
- attrType 39–42 → 主属性（影响 ATK 公式）
- attrType 87 → 源石技艺强度
- attrType 17/28/29/32/33/50–55/61/64–69 → 伤害加成（加法组）
- 条件型条目跳过（宁可低估）

验证：陈千语 潜能 2 → 敏捷 +15、物理伤害 +8%，ATK 1021 → 1060。

发行：https://github.com/starchfurrycon/endfield-team-sim/releases/tag/v1.2.0
产物 SHA256：`6EEDA9EFFB2255A02F28FE86E0A90B4AB40AF0DA9CDDB7F888B64F15EB089E96`（下载校验一致），55 项测试全绿。

## 追加轮七 · 装备数据的结构与下一步（未接入）

探查了装备表，结构是干净的，**可以做**，但需要一次专门的改动：

`TableCfg/EquipTable.json`（276 件），每件：
```json
"equipAttrModifiers": [
  {"attrType": 3,  "attrValues": [8.0, 8.0, 8.0, 8.0], "modifierType": 5},   // 防御
  {"attrType": 39, "attrValues": [15.0, 15.0, 15.0, 15.0]},                  // 力量
  ...
]
```
- `attrValues` 的 4 个值对应**精锻等级 0~3**（与 `displayAttrModifiers` 一致）
- `attrType` 与天赋表同义（39–42 主属性、1 生命、3 防御、50–54 伤害加成…）

`TableCfg/EquipSuitTable.json`（24 套）：3 件套触发 `skillID`（如 `passive_equipsuit_agi_01`），
对应 BuffData 里的被动——需要像天赋一样解析 `attributeModifier`。

**为什么这轮没接**：装备不是"干员自带"，而是玩家选择（套装 + 4 个部位 + 精锻等级），
必须新增一个 scenario 维度（`equip_suit` / `equip_level`），并决定"默认给什么装备"。
给一个拍脑袋的默认套装会直接污染排行榜，所以宁可暂时不加，也不做错误假设。

**下一轮计划**：
1. 解析 `EquipTable` 的 `equipAttrModifiers`（精锻 0~3）→ 每件装备的属性向量
2. 解析 `EquipSuitTable` 的 3 件套被动（走 BuffData → attributeModifier）
3. `Scenario` 增加 `equip_set: list[4 件]` 与 `equip_level: 0~3`，默认**空装备**（= 当前行为）
4. 提供 3~4 套"标准预设"（按属性套装，不按干员推荐），让用户能一键对比装备差异
