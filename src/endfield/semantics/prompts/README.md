# LLM 提示词工程说明

这套提示词的目标不是"让模型自由发挥"，而是**让模型只做它擅长的部分**：
把技能中文描述翻译成封闭枚举的机制标签；数值、倍率、帧数一律不碰。

```
技能文本 ──► [规则层] ──► 已确定？（trigger/元素/异常/置信度）
                 │ 否
                 ▼
          [LLM 标注] ──► schema 校验 ──► 证据校验 ──► 修复重试（1 次）──► 仍失败则丢弃
                 │ 通过
                 ▼
          [合并] 规则为主，LLM 只补"规则不知道"的字段；冲突写进复核报告
```

## 1. 契约

- 输入：`{operator, slot, name, element_hint, text}`（`text` 已去掉 wiki 模板标记）
- 输出：严格 JSON，字段见 `semantics_system.md` 里的 `{SCHEMA}`
- 硬约束：
  - 不给数值（`gives_sp` / `gives_ult` 会被代码强制清空）；
  - `element` / `abnormal` / `trigger` / `role` 只能取枚举值，不确定就 `null` / `unknown`；
  - `evidence` 必须是**原文逐字子串**（代码逐条检查）。
- `method` 由代码写回，不信任模型自报。

## 2. 为什么证据校验是核心

LLM 最容易犯的错不是"分类错"，而是**编造一个听起来合理的理由**。
所以每个实质性判断都要求引用原文，并由代码检查引用是否真的出现在文本里：

- 引用不在原文 → 整条标注重试（repair），仍失败则丢弃；
- 有实质判断但 `evidence` 为空 → 同样视为不合格；
- 没文本（如噗切娜在 BWIKI 无页面）→ **不调用**，直接返回 `None`，省 token 也不瞎猜。

这条规则把"幻觉"变成可检测的失败，而不是悄悄污染数据集。

## 3. 置信度标尺

| 值 | 含义 | 典型场景 |
|---|---|---|
| 0.9 | 文本明说 | "造成物理伤害并击飞" |
| 0.7 | 可推断 | "立盾期间受到攻击则反击"（触发与依赖受击的区分） |
| 0.4 | 弱线索 | 只提到状态名，不明确是否施加 |
| 0.2 | 无依据 | 无文本 / 纯猜测——禁止把猜测写成结论 |

合并时若与规则冲突，置信度被压到 ≤0.5，并写入复核报告的"冲突"段。

## 4. 提示词结构

| 文件 | 作用 | 关键设计 |
|---|---|---|
| `semantics_system.md` | 主标注提示 | 先写"不能做什么"，再给字段语义、易错规则、术语表、5 个示例 |
| `semantics_repair.md` | 校验失败后的修复 | 只允许修列出的错误；强制降低无证据字段的置信度 |
| `mechanics_system.md` | 未知黑板键归类 | 只输出报告，不改引擎；类别枚举固定 |
| `examples.json` | few-shot | 全部取自本项目真实技能文本（含受击连携、治疗、状态触发、空文本） |

为什么先写"不能做什么"：模型对"禁止项"的遵循度高于"要求项"，
而本项目最致命的错误是**把机制类标签当数值**或**编造条件**。

为什么示例里放"空文本 → unknown"：给模型一个"可以承认不知道"的示范，
比只写"不确定要标 unknown"更有效。

## 5. 版本与缓存

- `llm.py:PROMPT_VERSION` 参与缓存 key。
- 改提示词语义（字段含义/判定规则/示例）**必须 +1**，否则旧缓存会被复用，
  表现为"改了提示词但结果不变"。
- 缓存按 `(PROMPT_VERSION, model, 输入 payload)` 内容寻址，同一技能只计费一次。

## 6. 成本与延迟

- 默认 `gaps` 模式：只问规则不确定的技能（未知 trigger、缺元素、低置信度）；
  一个 35 人版本通常 10~30 次调用。
- `--mode all` 适合"换模型/改提示词后重新标注一遍"，会跑满 336 次（有缓存后很便宜）。
- `--limit N` 用于试水；`data/reports/llm-review.md` 会记录 tokens 与可选成本估算
  （`data/llm.json` 里填 `price_in` / `price_out`，单位：元/百万 token）。
- 失败重试只针对网络/限流/5xx（一次，1.2s 退避）；401/403 直接失败不重试。

## 7. 失败模式与处理

| 现象 | 处理 |
|---|---|
| 输出不是 JSON / 被 Markdown 包裹 | 提取首个 `{...}`；失败则 repair |
| 枚举越界（如 `trigger: "when_hit"`） | schema 校验失败 → repair 一次 |
| 证据不在原文 | 证据校验失败 → repair 一次 |
| 修不好 | 丢弃，保留规则结果；计入 `llm_rejected` |
| 429 / 超时 / 5xx | 退避重试一次；仍失败则跳过该技能（不阻塞整批） |
| 响应被截断 | 校验失败 → repair（提示里附错误） |

## 8. 怎么评估"prompt 好不好"

1. 看 `data/reports/llm-review.md` 的「被改写技能」表：每条都必须能对着原文点头；
2. 看「冲突」段：规则与 LLM 谁对，逐条判；
3. 看「仍为 unknown/低置信度」：如果大量技能卡在这里，说明提示词或 schema 需要补；
4. 回归：`python -m unittest tests.test_llm`（用假 transport，不联网、不花钱）。

## 9. 已知局限（写在明面上）

- 一个技能只标一个 `element`：混合元素技能（如"物理伤害…并造成灼热伤害"）
  会取主要元素并在 `notes` 标 `mixed_element`，引擎仍按单元素结算。
- 只处理技能文本：**新伤害机制 / 新 buff 叠加规则**无法从"分类标签"里获得，
  需要改引擎；这类会出现在 `data-quality.md` 与每次输出的 `unmodeled` 里。
- 模型对游戏专有名词的理解依赖示例与术语表；换新模型时建议先跑 `--mode all --limit 20`
  抽查一遍。
